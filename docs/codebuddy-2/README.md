# CodeBuddy 2.0 改造方案

> 状态：Draft，作为后续需求确认、技术设计和分阶段实现的权威入口。
>
> 本文档描述目标与边界；具体数据模型见 `technical-design.md`，实施顺序见 `implementation-roadmap.md`。

## 1. 背景

当前 `linc_codebuddy` 已具备仓库侦测、任务路由、work item、验证建议、巡检、分支与提交辅助，以及 Skill、CLI、MCP 三种入口。它能够较好地执行一个已经明确的开发任务，但仍主要依赖大模型临场判断：

- 新项目或模糊需求可能过早进入编码；
- 需求、设计、任务和验收之间缺少可追溯关系；
- 项目跨会话后不容易准确回答当前阶段、唯一焦点和下一步；
- 技术检查可以通过，但无法证明实现符合原始需求；
- 开发过程可能逐步偏离主线；
- 简单修改与高风险改造缺少稳定、可解释的差异化流程。

CodeBuddy 2.0 要解决的不是“让模型写更多代码”，而是让模型在合适的约束下持续做正确的事。

## 2. 产品定位

CodeBuddy 2.0 是面向个人开发者的自适应工程治理 Agent：

1. 把模糊想法收敛为可验证的需求；
2. 根据不确定性和风险自动选择流程深度；
3. 保存项目阶段、当前变更、当前任务、阻塞和下一动作；
4. 在高风险阶段设置可解释的准入门禁；
5. 调用现有编码 Agent 完成实现，而不替代编码 Agent；
6. 用测试和验收证据证明交付结果；
7. 通过 Git 和 GitLab 维护版本、评审、CI 与发布状态；
8. 对小事保持轻量，对复杂和危险事项加强治理。

## 3. 核心原则

1. **问题先于方案**：需求不清楚时先澄清，不直接编码。
2. **规格是依据**：复杂变更必须能从代码追溯到需求与验收。
3. **状态外化**：项目事实写入仓库和 GitLab，不依赖聊天记忆。
4. **一次一个焦点**：任何时刻明确 active change、active task 和 next action。
5. **自适应深度**：流程成本必须低于它降低的风险。
6. **小事快做**：简单、明确、可逆的任务走最短可信路径。
7. **风险升级**：实施中发现认证、权限、数据、生产或不可逆影响时自动升级。
8. **不能虚假完成**：任务完成必须关联具体 ID 和验证证据。
9. **测试不等于验收**：技术检查通过后仍需判断需求是否实现。
10. **受治理的自主性**：Agent 可推荐和执行低风险动作，重大决策与生产操作由人批准。

## 4. 借鉴与取舍

CodeBuddy 2.0 吸收以下开源项目的机制，但第一阶段不直接引入其运行时依赖：

| 来源 | 吸收的机制 | CodeBuddy 落点 |
|---|---|---|
| AutoGPT | 围绕目标选择下一动作 | `next`、workspace 巡检；不做无限自动循环 |
| MetaGPT | 产品、架构、开发、测试职责分离 | 生命周期阶段和独立审查视角；不模拟虚拟公司 |
| LangGraph | 有状态流程、条件分支、暂停和人工审批 | phase、gate、transition；稳定后再评估运行时 |
| CrewAI | 角色任务和顺序/并行编排 | 后期用于分析、实现、测试、评审编排 |
| Letta | 长期连续性 | Git 管理的项目状态、决策和证据优先 |
| OpenSpec | proposal/spec/design/tasks/verify/archive | change 目录和规范驱动变更 |
| Spec Kit | constitution/specify/plan/tasks/converge | 项目原则、需求规划和漂移检查 |
| BMAD | 按复杂度调整流程深度 | L0-L3 自适应治理 |
| Taskmaster | 稳定任务 ID、依赖和下一任务 | task graph、active task、next action |

明确不做：

- 不把 AutoGPT、MetaGPT、CrewAI、Letta 直接嵌入 V2 基础版本；
- 不用多 Agent 对话替代需求事实和工程证据；
- 不维护与 GitLab 冲突的第二套完整项目管理平台；
- 不为每次小修改生成一组空洞文档；
- 不允许 Agent 静默绕过高风险门禁。

## 5. 双轴工作模型

### 5.1 生命周期 Phase

```text
explore -> specify -> design -> plan -> implement
        -> verify -> release -> operate -> learn
```

- `explore`：明确问题、用户、现状、目标、约束和假设；
- `specify`：形成范围、需求和可测试验收场景；
- `design`：分析现有系统并选择技术方案；
- `plan`：拆分带依赖、完成条件和验证方法的任务；
- `implement`：按当前任务小步实现；
- `verify`：完成技术验证、行为验证和需求验收；
- `release`：形成版本、迁移、回滚和部署后验证方案；
- `operate`：跟踪运行状态、生产版本和问题；
- `learn`：复盘偏差，将经验写回项目规则与决策。

Phase 描述“项目或变更现在处于哪里”。

### 5.2 执行 Route

保留现有路由：

```text
new / continue / review / hotfix / ship
```

Route 描述“这一次会话采取什么动作”。例如：

```yaml
phase: specify
route: continue
```

表示本轮继续澄清需求，不能因为 route 是 `continue` 就修改业务代码。

## 6. 自适应治理等级

| 等级 | 典型场景 | 最小流程 | 必要产物 |
|---|---|---|---|
| L0 快修 | 文案、样式、小配置、根因明确且可逆的小错误 | 定位、修改、最小验证 | 状态中的目的和验证记录 |
| L1 标准 | 范围明确的小功能、普通 Bug、局部改动 | 简短任务、实现、针对性测试、Review | 一个结构化 change/work item |
| L2 设计 | 跨模块、API、数据库、认证、权限、生产行为 | 需求、验收、设计、任务、完整验证 | change + requirements + design + tasks + verification |
| L3 项目 | 新项目、模糊问题、关键架构、多个里程碑 | 探索、规格、架构、路线图、分阶段验收 | 项目级文档 + 多个 change |

分级至少考虑：需求不确定性、改动范围、数据影响、安全与权限、生产影响、回滚难度。

以下信号最低为 L2：

- 身份认证、授权和访问控制；
- 敏感数据、密钥或隐私；
- 数据迁移、删除或不可逆操作；
- 对外 API 或持久化协议兼容性；
- 生产环境行为或发布链路。

流程可在实施中升级。降级必须给出理由；高风险降级必须获得用户批准并留痕。

## 7. 核心能力

### 7.1 Project Init

初始化或接管项目，记录目标、用户、成功标准、环境、远端、保护动作、默认质量要求和当前版本。

### 7.2 Classify

对任务进行 L0-L3 分级，返回置信度、理由、风险信号、必要产物和允许省略的流程。

### 7.3 Change

建立稳定的 change ID，记录为什么做、做什么、不做什么、验收条件、风险和当前阶段。

### 7.4 Gate

在阶段转换前检查必要事实和产物，返回 `allowed`、缺失项与建议动作。门禁应帮助补齐信息，而不是只返回拒绝。

### 7.5 Next

根据项目状态、任务依赖、门禁和风险返回一个主要下一动作，并说明原因、能否改代码以及需要谁确认。

### 7.6 Verify

分开记录：

- 静态与构建检查；
- 单元和集成测试；
- API、页面及关键流程行为验证；
- Requirement -> Acceptance -> Implementation -> Test -> Evidence 追踪。

### 7.7 Drift

识别 diff、任务和项目目标之间的漂移，包括无需求依据的代码、超范围改动、设计变化未记录、提交增长但验收没有进展等。

### 7.8 Release

生成发布范围、迁移、配置变化、风险、回滚、部署后验证及 commit/tag 对应关系。生产执行继续要求明确人工批准。

### 7.9 Workspace Status

汇总多个项目的 phase、active change、active task、阻塞、风险、开发版本、生产版本和 next action。

## 8. 信息权威边界

| 信息 | 权威来源 |
|---|---|
| 项目目标、需求、设计、决策 | Git 仓库中的 CodeBuddy 文档 |
| 本地阶段、当前变更和当前任务 | CodeBuddy state |
| Issue、Milestone、MR | GitLab |
| 自动测试与构建结果 | CI 或本地 evidence |
| 发布版本 | Git Tag / GitLab Release |
| 生产版本 | Environment 或部署记录 |

CodeBuddy 可以建立引用和同步，但不得让多套状态在无冲突策略时同时成为权威。

## 9. 人工决策边界

以下情况 Agent 必须停下并请求确认：

- 真实需求或业务规则需要用户选择；
- 存在会显著改变范围、成本或架构的方案取舍；
- 提升权限或扩大外部系统范围；
- 生产部署、重启、数据迁移和删除；
- 不可逆操作；
- 高风险门禁降级或绕过。

低风险、可逆且处于已批准范围内的实现和验证可以继续自主执行。

## 10. 成功标准

CodeBuddy 2.0 达标时，应稳定做到：

1. 新项目不会在问题和成功标准不清楚时直接进入大规模编码；
2. 任意时刻都能回答当前阶段、唯一焦点、阻塞和下一步；
3. L0/L1 任务不会被不必要文档拖慢；
4. L2/L3 变更未经必要确认不能越级实施；
5. 任务不会因标题匹配或批量操作被错误标记完成；
6. 每个已完成需求都有对应验收和验证证据；
7. 能识别实现超范围和开发偏离；
8. 跨会话、跨 Agent 后仍可从仓库恢复可靠上下文；
9. GitLab 与仓库状态职责清晰；
10. 生产操作始终保留人工批准和回滚信息。

## 11. 非目标

V2 阶段不追求：

- 无人值守地自动完成整个项目；
- 同时运行大量角色 Agent；
- 替代 GitLab、CI 或现有测试框架；
- 自动推断并决定所有业务需求；
- 一次性支持所有语言和部署平台；
- 通过文档数量衡量工程质量。

## 12. 文档使用方式

后续模型接手时必须：

1. 先阅读本文件、`technical-design.md` 和 `implementation-roadmap.md`；
2. 检查仓库现有未提交改动，不覆盖未知修改；
3. 只执行当前里程碑，不提前实现后续能力；
4. 每项能力先补测试，再改变已有行为；
5. 发现方案假设不成立时更新文档并说明原因；
6. 完成里程碑后记录验证证据和剩余风险，再进入下一阶段。
