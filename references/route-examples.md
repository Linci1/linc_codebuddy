# Route Examples

当用户没有直接说 `new` / `continue` / `review` / `hotfix` / `ship` 时，用这些例子做路由判断。

## new

典型触发：

- “给这个项目加一个登录页”
- “帮我实现一个导入脚本”
- “把这个 skill 改造成 agent”

起手动作：

- 先做 repo intake
- 明确目标、范围、验收
- 判断是否需要正式 plan

交付重点：

- 代码改动
- 验证结果
- 任务记录

## continue

典型触发：

- “继续”
- “接着上次的 work item”
- “根据 review 意见改完”

起手动作：

- 先查当前 diff、任务文件、worklog
- 判断是否有未完成 Active 项
- 说明本次接着哪一段做

交付重点：

- 延续上下文
- 同步任务状态
- 明确剩余事项

## review

典型触发：

- “帮我 review 一下”
- “看看这次改动有没有风险”
- “做个代码审查”

起手动作：

- 默认不主动改代码
- 先看 diff、受影响文件、测试覆盖
- 按严重度列 findings

交付重点：

- findings 优先
- 风险说明
- 测试缺口

## hotfix

典型触发：

- “线上这个报错先修掉”
- “快速 patch 一下”
- “先做最小修复”

起手动作：

- 默认极速模式
- 先收缩问题范围
- 只做最小修复和必要验证

交付重点：

- 修复点
- 风险边界
- 是否还需要后续清理

## ship

典型触发：

- “帮我整理提交”
- “准备发出去”
- “给我一个可提交状态”

起手动作：

- 看当前 diff 和任务状态
- 补最小可信验证
- 整理 branch 和 commit 方案

交付重点：

- 核心变更范围
- 验证结果
- branch / commit 建议

## 默认判断顺序

如果一句话里同时有多个信号，按这个顺序判断主路由：

1. review
2. ship
3. hotfix
4. continue
5. new

原因：

- `review` 和 `ship` 主要是交付阶段动作，优先识别
- `hotfix` 对范围控制要求更强
- `continue` 依赖已有上下文
- 其余默认落到 `new`
