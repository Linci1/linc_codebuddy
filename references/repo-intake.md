# Repo Intake

进入一个仓库后，先做最小侦测，再决定要不要计划或实现。

## 1. 根目录与 Git 状态

优先执行：

```bash
git rev-parse --show-toplevel
git status --short --branch
```

需要确认：

- 当前工作目录是否已经在目标仓库内
- 当前分支是什么
- 是否存在未提交改动或未跟踪文件
- 目标文件是否已经有进行中的改动

如果不是 git 仓库，就把当前目录当作工作根目录，但要在回复里说清楚。

## 2. 技术栈侦测

优先看这些文件或命令入口：

- `scripts/dev`
- `Makefile`
- `justfile`
- `package.json`
- `pyproject.toml`
- `go.mod`
- `Cargo.toml`
- `Dockerfile`

目标不是把所有文件都读一遍，而是尽快回答：

- 这是哪类项目
- 用什么包管理器
- 最可能的验证命令是什么
- 是否已经有仓库级开发脚本

## 3. 任务介质侦测

按优先级查找：

1. 仓库已有 `TASKS.md`
2. 仓库已有 `docs/worklogs/`
3. `.codex/TASKS.md`
4. `.codex/worklogs/`

原则：

- 有现成约定就复用
- 没有就用 `.codex/` 回退
- 不为了一次性任务强行引入重流程

## 4. 路由判断

侦测完成后，快速判断进入哪条路由：

- `new`：仓库里还没有对应能力，需要从零到一补齐
- `continue`：已有上下文或已有半成品，需要接着做
- `review`：重点是发现问题，不是立刻改
- `hotfix`：问题范围明确，优先最小修复
- `ship`：重点是差异整理、验证、提交、推送准备

## 5. 何时正式计划

满足任一条件时再进入正式 plan：

- 改动跨多个模块
- 用户给了多个验收条件
- 需要先探索技术方案
- 需要多轮验证或迁移

否则可以直接小步快跑，但仍要在输出中写清假设和验证结果。
